## 2. The blocker: the contract must live on Studio Next (chain 61997)

The form accepts only Studio Next links. Mandate Guard is deployed on **studionet (chain 61999)**
at `0xbd70CB985fA5D581aA7b83c1e27EBf3D1293593b` (CP4), and that is the address the frontend, the
README table and the demo script all point at.

I tried to close this directly rather than report it. What I found:

- Studio Next's RPC resolves two ways: canonical `https://studio-dev.genlayer.com/api` and the
  browser alias `https://studio-next.genlayer.com/api`. Both report `eth_chainId = 0xf22d` (61997).
  Verified by direct JSON-RPC call.
- I added a `studio-next` network entry to `gltest.config.yaml` and deployed through
  `deploy/deploy_mandate_guard.py --network studio-next`. It failed validation first (custom
  networks need `id` **and** an `accounts` list of private keys), so I dropped that approach and
  wrote a one-off `scratch/deploy_studio_next.py` that builds the chain descriptor in-process and
  keeps any key in gitignored `scratch/`. That got as far as:
  `Transaction reverted: EVM tx 0x341a9f3d… to consensus contract 0xb7278A61… was reverted.`
  Account `0x40f396bB04eB886d3711d02ca60bb631DC16b9CA`, `eth_getBalance = 0x0`,
  `eth_gasPrice = 0x0`.
- The docs explain why. Chain 61997 is the **v0.123 / Consensus v0.6 release-candidate preview**:
  *"Use the matching release-candidate SDK or CLI and its explicit `studioDevnet` / `studio-dev`
  network preset. Do not relabel the stable `studionet` preset: the environments have different
  chain IDs and deployments."* and *"Do not point the stable `studionet` chain object at the
  preview RPC: chain identity and consensus contract addresses must move together."*
  The compatible family is CLI v0.40 RC, `genlayer-py` v0.19 RC, `genlayer-js` v2.0 RC, Studio
  v0.123 RC, plus a v0.6-compatible `gltest` prerelease. Under v0.6 *"every deploy and write must
  carry a `FeesDistribution` and its quoted fee value"*, sourced from a `fee-profile.json`
  generated by `gltest --fee-profile`. A Studio deployment *can* still be gasless, but that has to
  be detected from the fee estimate, not assumed from the network name.
- The installed CLI (0.39.2) has no `studio-dev` alias: `genlayer network list` shows only
  localnet / studionet / testnet-asimov / testnet-bradbury. npm has 0.40.0-rc1 / rc2 / rc3 /
  clarke available.

**So this is a stack migration, not a config tweak:** new CLI (global install), RC `genlayer-py`,
RC `gltest`, a fee profile, and possibly a newer GenVM runner hash in the contract header. The
project deliberately pinned the stable, proven-on-studionet stack (`HANDOVER_STEP3.md`: *"Never use
a `latest` or test alias… days from a deadline"*). Doing this now, while the 61-test suite and the
demo depend on the current pins, is a real risk with about two hours on the clock.

Both routes need a decision from the principal, not from me:

- **(A) Migrate to the RC stack and deploy to Studio Next.** Needs: permission for a global
  `npm i -g genlayer@0.40.0-rc.3`, RC pip installs (ideally in a throwaway venv under `scratch/`
  so the pinned suite and `requirements.txt` are not disturbed), a fee profile, and possibly
  faucet funds (the Studio-dev faucet is the 💧 button in the Studio web app, which needs a
  browser wallet and a human).
- **(B) Submit pointing at the studionet deployment.** Cheapest and honest, but the form's
  contract-link field is stated as a requirement, so it may simply refuse the submission.

I have not started (A): it changes the toolchain the whole submission rests on, on deadline day.

### 02 One-liner (limit 180, draft is 177)

### 03 What is this project? (limit 1000, draft is 990)

> Agent payment rails handle numbers well: price caps, spend limits. The problem is that half of
> what people write in an instruction is not a number. "Prefer refundable." "A reputable seller."
> Nothing enforces a sentence like that, and in AP2 the thing checking the cart against your intent
> is your own agent, the part most likely to be compromised.
>
> Mandate Guard moves that check somewhere neither party controls. You write the mandate in
> English. The operator posts a bond at least as large as the mandate allows spending, then
> transacts immediately. Nothing in the purchase path waits on a judge. Every purchase lands
> on-chain with its evidence. Anyone can challenge inside a window, and validators then fetch the
> live listing themselves, each re-deriving a verdict with their own LLM. Out of mandate, the bond
> is slashed to the principal. Within mandate, the challenger loses the deposit. The verdict is
> stored: within_mandate, clause_violated, severity, reasoning, and every payout leg.

### 05 How-to steps

1. **Run the fast tests** — `pip install -r requirements.txt && pytest tests/direct/ -q` → 61
   passed, no network needed (web and LLM calls are mocked). On Windows the suite applies a small
   compatibility patch in `tests/direct/conftest.py` for a known gltest file-locking bug.
2. **Read the contract** — `contracts/mandate_guard.py`. `register_mandate` takes the bond as
   payable value, `record_action` is operator-only, `challenge` requires the exact deposit the
   contract reports through `required_deposit`, `resolve` is permissionless and settles.
3. **Lint it** — `genvm-lint check contracts/mandate_guard.py` → lint and validation pass,
   10 methods (6 view, 4 write).
4. **Watch the judgment end to end** — `python demo/run_demo.py` (about two minutes; `resolve`
   alone is 55–65s of real multi-validator consensus over a real page fetch). It registers the
   mandate, records a compliant purchase (refundable Flex Economy $220), records a deliberately
   drifting one (non-refundable Basic Saver $180), challenges the drift, and prints the verdict.
5. **Run the UI** — `frontend/`, `npm install && npm run dev`, connect a wallet to the network in
   the README table. The mandate editor, the action feed and the verdict panel are the three
   surfaces.

### 06 Expected verification outcome (limit 500, draft is 499, stewards only)

> Expect `within_mandate: False`, `clause_violated` quoting the "prefer refundable" clause,
> `bond_intact: False`, and two payout legs: the full 250 GEN bond to the principal, 25 GEN deposit

> finalization, so the evidence is the on-chain payout record and the contract's balance movement,

## 4. Disclosure the submission owes the reader

These are obligations already recorded in the project's own docs, not new additions:

- The demo merchant page is hosted by us (`demo-listing/`, served via GitHub Pages), so the review
  does not depend on a third party's page surviving until judging. The validator fetch is still a
  real fetch of a real public URL over the open internet. (D5 / P7 obligation.)
- The challenger incentive gap: a failed challenge loses the deposit, a successful one only
  returns it, so no third party is actually motivated to challenge. Only the principal is. (D6.)
- Settlement is blunt: severity is recorded but does not scale the payout, so a small deviation
  costs the whole bond. (D13.)
- The mandate says "$250" while the bond and deposit are GEN-wei. The ceiling is a declared wei
  parameter, never parsed out of the prose, and the two are not formally linked. (USD/GEN seam.)
- An action can be challenged once ever, not once at a time. (One-challenge rule.)
- Direct-mode tests prove payout **intent** (recipient, exact wei, finalization), not balance
  movement. Balance movement is proven only on-chain. (D11.)
